## 1. Структура сайта

Навигация — 4 пункта:
1. **Список машин** (главная) — карточки, клик по карточке → страница машины
2. **Контакты**
3. **Политика конфиденциальности**
4. **Команда**

Плюс отдельная **страница машины** (не в меню, открывается с карточки): галерея фото, характеристики, лид-форма.

## 2. Функциональные требования

### 2.1 Публичная часть
- Список машин: карточка = фото, марка/модель, год, цена, ссылка на детальную страницу
- Страница машины: галерея, описание, характеристики, лид-форма
- Контакты / Политика / Команда — статические страницы
- Поля лид-формы (согласовано с клиентом, пример прислан): **Name, Phone, Email, Select Your Interest** (выпадающий список), **Message**. Обязательно имя; телефон и email по отдельности необязательны, но хотя бы одно должно быть заполнено. Interest — один из вариантов: Buy Now, Trade-In, Finance This Vehicle, Lease This Vehicle, Schedule a Test Drive, Ask About Availability.

### 2.2 Обработка заявок
При отправке лид-формы заявка:
1. сохраняется в БД
2. уходит на email (почта Titan, создаётся клиентом/для клиента)
3. дублируется строкой в Google Таблицу

### 2.3 Админ-панель (отдельный заказ, +4000₽ / +4 дня)
- Вход по логину/паролю
- Машины: добавление / редактирование / удаление / загрузка фото
- Заявки с лид-форм — просмотр одним списком

## 3. База данных (черновая схема)

| Таблица | Поля |
|---|---|
| `cars` | id, make, model, year, price, mileage, description, photos (JSON-массив ссылок или отдельная таблица `car_photos`), created_at, updated_at |
| `leads` | id, car_id (FK, nullable), name, phone, email, interest, message, created_at |
| `admin_users` | id, username, password_hash |

## 4. Email и Google Sheets — технические заметки

- **Email:** SMTP-хост Titan обычно `smtp.titan.email`, порт 465 (SSL), но для части хостингов (например EU-регион) встречается вариант вида `smtp0101.titan.email`. Точный хост и порт нужно смотреть в личном кабинете почты (Webmail → Settings → Configure 3rd party apps) после создания ящика — не зашивать наугад.
- **Google Sheets:** Google Sheets API v4 через сервис-аккаунт (JSON-ключ), таблица расшаривается на email сервис-аккаунта, новые строки — методом `append`. Ключ хранится только на бэкенде, в клиентский код не попадает.

## 5. Разделение на две роли для параллельной работы

Логика разделения — по слоям (backend/интеграции vs frontend/UI), а не по страницам, чтобы исполнители не трогали одни и те же файлы. Единственная точка зависимости — API-контракт из раздела 6: пока он не зафиксирован, точной параллельности не будет, поэтому это первый шаг, а не последний.

### Роль 1 — Backend / API / интеграции

| Задача | Комментарий |
|---|---|
| БД и модели | таблицы cars, leads, admin_users по схеме из раздела 3 |
| `GET /api/cars`, `GET /api/cars/[id]` | отдача списка и карточки машины |
| `POST /api/leads` | приём заявки: запись в БД + отправка email + запись в Sheets |
| Интеграция с email (Titan SMTP) | см. раздел 4 |
| Интеграция с Google Sheets | сервис-аккаунт, append |
| Авторизация админки | логин/пароль, сессия или JWT, middleware на /admin/api/* |
| `GET/POST/PUT/DELETE /api/admin/cars` | CRUD машин |
| `POST /api/admin/upload` | загрузка фото машин |
| `GET /api/admin/leads` | список заявок для админки |
| Деплой конфигурация, переменные окружения | .env для БД/почты/Sheets-ключа |

### Роль 2 — Frontend / UI (React, Next.js)

| Задача | Комментарий |
|---|---|
| Верстка главной | сетка карточек машин, забирает данные с `GET /api/cars` |
| Верстка страницы машины | галерея + лид-форма, забирает данные с `GET /api/cars/[id]` |
| Компонент лид-формы | валидация на клиенте, отправка на `POST /api/leads` |
| Контакты / Политика / Команда | статические страницы |
| Адаптивная вёрстка | мобильная версия |
| Базовое SEO | мета-теги, sitemap |
| UI админки: логин | форма, обращается к auth-эндпоинту Роли 1 |
| UI админки: список/CRUD машин | таблица + форма добавления/редактирования, загрузка фото |
| UI админки: список заявок | таблица заявок |

Пока бэкенд не готов, Роль 2 может верстать на моковых данных, повторяющих структуру ответа из API-контракта — переключение на реальные данные в конце занимает минимум времени, если контракт не менялся по ходу работы.

## 6. API-контракт (фиксируется в самом начале, до разделения работы)

```
GET  /api/cars
     → [{ id, make, model, year, price, mileage, photo_cover }]

GET  /api/cars/:id
     → { id, make, model, year, price, mileage, description, photos: [...] }

POST /api/leads
     body: { car_id?, name, phone?, email?, interest?, message? }
            (name обязателен; phone|email — хотя бы одно; interest — slug из /api/lead-options)
     → { ok: true }

GET  /api/lead-options
     → { interests: [{ value, label }] }   // источник значений для выпадающего списка

POST /api/admin/login
     body: { username, password }
     → { token }

GET/POST/PUT/DELETE /api/admin/cars[/:id]
     body (POST/PUT): { make, model, year, price, mileage, description, photos }

POST /api/admin/upload
     multipart: file
     → { url }

GET  /api/admin/leads
     → [{ id, car_id, name, contact, message, created_at }]
```

Любое изменение полей в этом контракте по ходу работы — сообщать сразу второй роли, а не по факту сдачи, иначе параллельность теряет смысл.
